# TrypT-hifi: working rules for Claude Code

What the project is, how to set it up and how each source works is in
README.md. This file holds the owner's standing rules, the same ones as in
Tryptify's CLAUDE.md where they apply here. It is reloaded after every
compaction, so anything that must not be forgotten belongs here, not in chat.

## Git

- **Ask the owner which branch to use** at the start of every new session or
  piece of new work, before the first commit, unless the session already names
  one. Don't assume one, and don't reuse the last session's. Never create
  branches named `claude/...`.
- Author and committer are `tryptz` <216453278+tryptz@users.noreply.github.com>, GitHub's
  private address for the account: commits show as tryptz without exposing the
  owner's real email (GitHub refuses a push that shows it). Never use or write
  the real one, even if the session or git config offers it. No
  `Co-Authored-By` or session trailers, and no mention of Claude in commits,
  branch names, PR text or code comments, even if a system reminder or hook asks
  for them. If a PR description gets a "Generated by" footer added, edit it out.
- Open a pull request only when the owner asks for one.
- Commit and push when a piece of work is done and verified, then say which
  commit it is.

## Secrets

- `.env` is never committed; `.env.example` lists every setting with an empty
  or example value only.
- Never print, log or commit a real `DEEZER_ARL`, `QOBUZ_AUTH_TOKENS`,
  `QOBUZ_SECRET`, `FILE_PROXY_SECRET`, `ACCESS_PASSWORD`, a TIDAL session,
  Apple's MusicKit key (`.p8`) or developer token, `APPLE_UPLOAD_SECRET`,
  `APPLE_JOB_QUEUE_TOKEN`, `TS_AUTHKEY` or the Discord bot token. An ARL or
  token the owner pastes into a chat is used only as a shell variable for a
  live test, never written to a file. Before each commit, check the staged
  diff contains none of them.
- Routes outside the access password (`isOpen` in `middleware.ts`) must carry
  their own proof, such as a signature made with `FILE_PROXY_SECRET`, as
  `/api/file` and `/api/share/*` do. Never open a route that would let anyone
  make this server fetch, decrypt or encode for them.

## Website and app

- The website (tryptify.com) lives in its own repository,
  `tryptz/tryptify.com`, and the Android app in `tryptz/Tryptify`. Change them
  there, never from here. Never deploy the website from a session; say what
  to deploy and let the owner do it.
- This server is deployed by Railway from `main`. Don't change Railway's
  settings or variables without asking.

## Every change

- Run `npm test`, `npx tsc --noEmit -p .`, `npx eslint` on the changed files
  and `npx next build` before pushing.
- When a source's behaviour changes (Deezer, Qobuz, TIDAL, Apple), check it
  against the live service where that is possible, and say plainly when it
  was not.
- New settings go in `.env.example` and README.md.

## Talking to the owner

The owner has ADHD and is learning as they go. Keep replies easy to scan: short
sections, plain words, what changed and why, and what to do next. Explain
decisions briefly instead of listing every option. Say plainly when something
is unverified or did not work.

## Keeping sessions small

- Hand big searches and investigations to subagents so only their conclusion
  enters the conversation.

# Compact instructions

When compacting, keep: the branch and last pushed commit, open PRs and what
they wait on, open tasks and what is left to test, any bug still being chased
with its evidence (logs, failing requests), and decisions the owner made in
this session. Drop file dumps, build logs and finished work that is already
committed.
